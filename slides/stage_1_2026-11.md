# Intl Supported Time Zone Options
## For Stage 1
### Shane F Carr — November 2026 TC39

---

## Background: Time Zone Enumeration

ECMA-402 provides two APIs that enumerate primary time zone identifiers:
- `Intl.supportedValuesOf("timeZone")` — primarily used for UI time zone pickers
- `Intl.Locale.prototype.getTimeZones()` — time zones for a locale's region

In IANA TZDB and CLDR (`timezone.xml`), primary zones fall into two categories:
- **Location-based zones** (associated with an ISO 3166-1 country/region):
  `"America/New_York"`, `"Europe/Berlin"`, `"Asia/Tokyo"`, …
- **Non-location zones** (assigned to world region `"001"` in CLDR):
  `"UTC"`, fixed-offset `"Etc/GMT±N"`, and legacy POSIX `"EST5EDT"`, `"CST6CDT"`, `"MST7MDT"`, `"PST8PDT"`

---

## Problem 1: Cross-Browser Divergence (#778, #1052)

ECMA-402 specifies returning all `AvailablePrimaryTimeZoneIdentifiers()`, yet engines diverge on non-location zones:

| Time Zone Category | Examples | Chrome (V8) | Safari (< 26) | Safari (26+) | Firefox |
| :--- | :--- | :---: | :---: | :---: | :---: |
| Location-based | `"America/New_York"` | Included | Included | Included | Included |
| UTC | `"UTC"` | Omitted | Included | Included | Included |
| Fixed-offset `Etc/GMT*` | `"Etc/GMT+5"` | Omitted | Omitted | Included | Included |
| Legacy POSIX | `"EST5EDT"` | Omitted | Omitted | Omitted | Omitted* |

*\*Firefox specifically patched `supportedValuesOf` to omit legacy POSIX zones.*

`new Intl.Locale("en-001").getTimeZones()` also diverges: returns `Etc/GMT*` and `SystemV/*` in Chrome/Safari vs. `[]` in Firefox.

---

## Problem 2: TZDB 2026d Un-deprecated Legacy Zones (#1103)

- **TZDB 2024b:** Deprecated `EST5EDT`, `CST6CDT`, `MST7MDT`, `PST8PDT` as `Link`s to city zones (`America/New_York`, etc.).
- **TZDB 2026d & CLDR 48:** Restored them as primary `Zone`s observing perpetual POSIX US DST rules — even if US/Canadian jurisdictions abolish DST!
- **Impact on Web Users:**
  - Under the current spec, `Intl.supportedValuesOf("timeZone")` must return them.
  - Users searching a picker for `"EST"` or `"PST"` may select `EST5EDT` or `PST8PDT`, breaking their local civil time if their jurisdiction later drops DST.
  - Re-aliasing them to cities in ECMA-402 breaks once no city observes those rules.

---

## Stage 1 Problem Statement

Agreed by ECMA-402 / TG2 ([Issue #3](https://github.com/tc39-transfer/proposal-intl-supported-time-zone-options/issues/3)):

> Engines diverge in the set of zones that are returned from `Intl.supportedValuesOf`. We want to align engines on a default behavior, while also researching use cases to tailor the set in various ways.

---

## Proposed Default Behavior

<div class="columns">
<div>

By default, return **location-based primary time zones + `"UTC"`**:
- Includes `"UTC"` (needed for servers, logs, and default system zones; [#2](https://github.com/tc39-transfer/proposal-intl-supported-time-zone-options/issues/2))
- Excludes `"Etc/GMT±N"` (sign-inverted POSIX offsets; full-hour only)
- Excludes `"EST5EDT"` etc.
- Aligns `Locale("en-001").getTimeZones()` to `["UTC"]`

</div>
<div>

```javascript
const zones =
  Intl.supportedValuesOf("timeZone");

zones.includes("America/New_York"); // true
zones.includes("UTC");              // true

zones.includes("Etc/GMT+5");        // false
zones.includes("EST5EDT");          // false

// Still valid in Temporal & DateTimeFormat!
Temporal.ZonedDateTime.from(
  "2026-11-30T10:00[Etc/GMT+5]"
);
```

</div>
</div>

## Stage 1 Exploration: Tailoring the Returned Set

<div class="columns">
<div>

**Strawman in Explainer:**
```javascript
Intl.supportedValuesOf("timeZone", {
  // "utc" (default)
  // | "none"
  // | "offset"
  // | "all"
  includeNonLocation: "offset",
});
```

</div>
<div>

**Questions to Research in Stage 1:**
- **Need for options:** Are there non-picker use cases requiring comprehensive enumeration, or is aligning the default sufficient?
- **Footgun-free naming:** `"all"` sounds appealing to picker authors — if legacy zones can be enumerated, name the option explicitly.
- **Aliases ([#1](https://github.com/tc39-transfer/proposal-intl-supported-time-zone-options/issues/1)):** Should non-primary `Link`s (`"US/Eastern"`, `"Asia/Calcutta"`) also be supported?

</div>
</div>
