# Intl Supported Time Zone Options
## For Stage 1
### Shane F Carr — November 2026 TC39

---

## Background: Time Zone Enumeration

- **ECMA-402 enumeration APIs:**
  - `Intl.supportedValuesOf("timeZone")` — for UI pickers
  - `Intl.Locale.prototype.getTimeZones()` — per-region zones
- **Categories in IANA TZDB & CLDR (`timezone.xml`):**
  - **Location-based:** `"America/New_York"`, `"Asia/Tokyo"`, …
  - **Non-location (`"001"`):** `"UTC"`, `"Etc/GMT±N"`, `"EST5EDT"`, …

---

## Problem 1: Cross-Browser Divergence (#778, #1052)

| Primary Zone Category | Example | Chrome | Safari <26 | Safari 26+ | Firefox |
| :--- | :--- | :---: | :---: | :---: | :---: |
| Location-based (~418) | `"America/New_York"` | ✅ | ✅ | ✅ | ✅ |
| UTC | `"UTC"` | ❌ | ✅ | ✅ | ✅ |
| Fixed-offset `Etc/GMT*` | `"Etc/GMT+5"` | ❌ | ❌ | ✅ | ✅ |
| Legacy POSIX | `"EST5EDT"` | ❌ | ❌ | ❌ | ❌* |

*\*Firefox specifically filters out legacy POSIX zones.*

- `Locale("en-001").getTimeZones()` diverges: 50 `Etc/*`, `SystemV/*` zones vs. `[]` in Firefox

---

## Problem 2: TZDB 2026d Restored POSIX Zones (#1103)

- **TZDB 2024b → 2026d:** `EST5EDT`, `CST6CDT`, `MST7MDT`, `PST8PDT` were `Link`s in 2024b; **TZDB 2026d & CLDR 48** restored them as primary `Zone`s
- **Cannot re-alias in ECMA-402:** JS math must match TZDB, and no city alias remains if all cities in a zone abolish DST
- **Picker hazard:** `"PST8PDT"` formats identically to `"America/Los_Angeles"` (`"Pacific Time"`), breaking users by 1 hr if their jurisdiction drops DST

---

## Non-Location Zone Tradeoffs: `"UTC"` vs. `Etc/GMT*`

- **`"UTC"` belongs in the default ([#2](https://github.com/tc39/proposal-intl-supported-time-zone-options/issues/2)):** Needed for servers, logs, and cross-region tools (omitted in Chrome)
- **`"Etc/GMT±N"` hurts default UI pickers:**
  - **Inverted POSIX signs:** `"Etc/GMT+5"` formats as `"GMT-05:00"` (`UTC−5`)!
  - **Whole hours only (`-14`..`+12`):** Omits `+05:30` (India), `+05:45` (Nepal), `+09:30`
  - **ISO offsets already work:** `Temporal` & `DateTimeFormat` accept `"-05:00"`, `"+05:30"`

---

## Stage 1 Problem Statement

Agreed by ECMA-402 / TG2 ([Issue #3](https://github.com/tc39/proposal-intl-supported-time-zone-options/issues/3)):

> Engines diverge in the set of zones that are returned from `Intl.supportedValuesOf`. We want to align engines on a default behavior, while also researching use cases to tailor the set in various ways.

---

## Proposed Default Behavior

<div class="columns">
<div>

Return **location-based primary zones + `"UTC"`**:
- Includes `"UTC"` ([#2](https://github.com/tc39/proposal-intl-supported-time-zone-options/issues/2))
- Excludes `"Etc/GMT±N"`
- Excludes `"EST5EDT"`, `"PST8PDT"`, …
- `Locale("en-001").getTimeZones()` → `["UTC"]`

</div>
<div>

```javascript
const zones =
  Intl.supportedValuesOf("timeZone");

zones.includes("America/New_York"); // true
zones.includes("UTC");              // true
zones.includes("Etc/GMT+5");        // false
zones.includes("EST5EDT");          // false

// Still valid in Temporal & DateTimeFormat:
Temporal.ZonedDateTime.from(
  "2026-11-30T10:00[Etc/GMT+5]"
);
```

</div>
</div>

## Stage 1 Exploration: Tailoring the Set

<div class="columns">
<div>

**Strawman in Explainer:**
```javascript
Intl.supportedValuesOf("timeZone", {
  // "utc" (default)
  // | "none"
  // | "offset"
  // | "includeLegacy"
  includeNonLocation: "offset",
});
```

</div>
<div>

**Stage 1 Research Questions:**
- **Options needed?** Default-only vs. non-picker enumeration
- **Safe naming:** Avoid `"all"` (misleads picker authors)
- **Aliases ([#1](https://github.com/tc39/proposal-intl-supported-time-zone-options/issues/1)):** Non-primary `Link`s (`"US/Eastern"`)?
